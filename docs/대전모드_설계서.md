# FLAG GAME 대전 모드 설계서 (Claude Code 인계용)

- 작성일: 2026. 11. 17.
- 대상 저장소: `bbonng/flaggame` (GitHub Pages, 공개)
- 한 줄 요약: 지금 혼자 하는 FLAG GAME의 **컴퓨터 "수비 코치" 자리에 다른 학생을 앉혀**, 반 전체가 무작위·익명으로 1:1 대결을 여러 판 하는 모드를 Firebase로 만든다.

---

## 0. 이 도구는 누구를 위한 것인가

학생. 지금 학생들은 공격 작전만 설계한다. 대전 모드의 목적은 **수비를 고르는 쪽도 공간을 읽게 하는 것**이다.
승패·순위·화려함은 수단이다. 구현 중 선택이 갈리면 "학생이 공간을 더 생각하게 되는 쪽"을 고른다.

## 1. 지금 코드 (확인한 사실)

| 항목 | 내용 |
|---|---|
| 파일 | `index.html`(약 4.8MB, three.js·GLTFLoader·X Bot 캐릭터 내장 단일 파일), `board.html`(TV 순위표), `apps-script/Code.gs`(점수 시트) |
| 엔진 | 공간작전판(flagboard) v12의 판정·수비 움직임·3D를 그대로 사용. 경기 진행만 `FLAG GAME` 구역(`LEVELS`, `G`, `coach()`, `setupDown()`, `snapGame()`, `nextDown()`, `nextDrive()`, `endGame()`)이 맡음 |
| 경기 규칙 | 골까지 25야드(`START_G`)에서 4다운, 터치다운 6점(1다운 TD +1), 추가점 5야드 1점 / 12야드 2점(`CONV_G`), 한 경기 드라이브 5번(`DRIVES`) |
| 수비 결정 | `coach()`가 `{actual, shown, say}`를 돌려줌. `actual`=실제 대형, `shown`=스냅 전 보여줄 대형(위장). 대형 키: `'2-2'`, `'3-1'`, `'4across'`, `'man'`, `'blitz'` |
| 난이도 | `LEVELS[1]` = 주전: `lag 0.30`, `ballReact 0.50`, `rush 3.0`, `rate 0.8`, `guide 'space'`, `zones true` |
| 공격 입력 | 작전(`S.off`, `S.paths`, `S.roles`, `S.mode`) + 플레이 중 `throwTo(rid)` (던진 순간 `t`는 0.1초 단위로 반올림) |
| 작전 직렬화 | `encodePlay()` / `decodePlay(code)` 가 이미 있음 (조 보관함 저장에 사용, `PLAY_VER`) |
| 결정론 | `simulate()`는 고정 간격 `R.dt = 0.05`의 규칙 기반 계산. `Math.random()`은 3D 장식(구름·잔디·관중·애니메이션 시작 위치)과 `uid()`에만 쓰임 → **같은 입력이면 어느 기기에서나 같은 결과** |
| 조 보관함 | 수업용 Apps Script(`STORE_URL_DEFAULT`)에 반·조·PIN으로 로그인해 작전 1·2·3 불러오기 |
| 점수 저장 | `GAME_STORE_URL`(현재 빈 값) → FLAG GAME 전용 시트. `score_submit`, `score_board` |

※ 결정론은 코드 읽기로 확인한 것이고 실제 두 기기 비교 실행은 아직 안 했다. → M1의 첫 검증 항목.
※ 2026. 11. 19. 코드 대조 결과와 보완점: [`M0_코드확인.md`](M0_코드확인.md)

## 2. 목표와 비목표

**목표**
1. 각자 웨일북에서 1:1 대결 (공격 ↔ 수비, 드라이브마다 교대)
2. 교사가 누르면 한 반(약 30명)이 동시에 무작위·익명으로 매칭되는 라운드 운영
3. 조별 평균 승점만 TV에 표시

**비목표 (하지 않는다)**
- 10명 실시간 조종, 선수 직접 조작(이번 단계에서는)
- 개인 순위표, 상대 이름 공개
- 기존 혼자 하는 모드·기존 순위표·`board.html`의 동작 변경
- 수업용 시트(작전 설계도·평가)와의 데이터 혼합
- 부정행위 방지(결과는 공격 쪽 기기 계산을 믿는다. 교실 수업용)

## 3. 경기 규칙 (확정)

**한 판**
- 각자 **공격 드라이브 1번씩**. 드라이브 = 골까지 25야드, 4다운, TD 6점(+1다운 보너스 1), 추가점 1/2점 — 기존 규칙 그대로.
- 점수 높은 쪽 승리. **동점은 무승부**(연장 없음).
- 선공은 무작위.
- 난이도는 주전(`LEVELS[1]`) 고정. 양쪽 기기가 같은 `R` 값을 써야 한다.

**다운 한 번의 흐름**
1. 다운 시작. 공격 **40초**, 수비 **15초** 작전 시계가 동시에 돈다.
2. 수비: 실제 대형 1개 선택 + (선택) 위장 대형 선택. 위장은 **드라이브당 1번**.
3. 수비가 확정하면 공격 화면에 `shown` 대형이 나타난다. 그 전까지는 "수비가 고르는 중".
4. 공격: 작전을 짜거나 조 보관함 작전을 불러와 고친 뒤 [스냅].
5. 공격이 실시간으로 플레이(기존과 동일, `throwTo`).
6. 결과 확정 → **양쪽에 공개 카드**: 실제 수비 대형, 위장 여부, 던진 리시버·라우트, 전진 야드. 수비 쪽은 같은 장면을 3D/2D로 다시 본다.
7. 다음 다운 또는 드라이브 종료.

**시간 초과**
- 수비 15초 초과 → 직전 다운의 대형(첫 다운이면 `'2-2'`), 위장 없음.
- 공격 40초 초과 → 현재 판에 놓인 작전으로 자동 스냅. 라우트가 하나도 없으면 `newGame()`의 기본 작전(spread: W1 go, W2 slant, W3 out, C hitch).
- 스냅 후 던지지 않으면 기존 판정(색/못 던짐) 그대로.

**라운드**
- 라운드 제한 **9분**. 끝나지 않은 판은 그 시점 점수로 판정.
- 한 차시 = 연습 5분 + 3라운드를 기본으로 본다.
- 시계 값(40/15초, 9분)은 모두 설정값으로 빼 둔다. 40초는 추정치라 수업에서 재 보고 고친다.

**승점**
- 승 3 · 무 1 · 패 0.
- 개인 전적은 본인 화면에만. TV에는 **조별 평균 승점**(5명 조·6명 조가 섞여 있어 합산이 아닌 평균).

## 4. 매칭 (확정)

- 무작위·익명. 화면에는 "상대"로만 표시. 끝난 뒤에도 공개하지 않는다.
- 같은 조끼리, 직전 라운드 상대는 피한다(불가능하면 허용).
- 홀수면 남는 1명은 기존 수비 코치와 드라이브 1번(연습 경기). 승점은 무승부와 같은 1점. ← 기본값, 바꿀 수 있음(11절).
- 매칭은 **교사 기기가 계산해서 기록**한다. 서버 코드(Cloud Functions) 없이 가기 위함.

## 5. 동기화 방식

화면을 실시간으로 보내지 않는다. **입력만 주고받고 각 기기가 같은 장면을 직접 계산**한다(1절의 결정론).

다운 한 번에 오가는 데이터:

```
수비 → { actual, shown }                      // 대형 키 2개
공격 → { play: encodePlay(), mode }           // 스냅 시
공격 → { throw: { rid, t } | null }           // 던진 순간(0.1초 단위) 또는 안 던짐
공격 → { result: { k, gain, td, who, how } }  // playOutcome() 결과
```

- 수비 기기는 `play` + `actual` + `throw`로 `simulate()`를 다시 돌려 같은 장면을 본다.
- 수비 기기가 계산한 결과와 공격이 보낸 `result`가 다르면 콘솔 경고 + 공격 쪽 값을 채택(개발 중에는 화면에도 표시).
- 방 데이터에 `engineVer`(`PLAY_VER` + 대전 모드 버전)를 넣고, 다르면 입장 거부 + "새로고침 하세요".
- **1차 구현은 수비가 결과 확정 뒤 리플레이로 본다.** 스냅과 동시에 따라 보는 실시간 관전은 그다음.
- 작전 시계는 Firebase 서버 시각 기준(`.info/serverTimeOffset`)으로 양쪽을 맞춘다.

## 6. Firebase 구성

- 제품: **Realtime Database + 익명 로그인**. Firestore·Cloud Functions는 쓰지 않는다.
- 요금제: 무료(Spark). 동시 접속 100개 한도 → **한 번에 한 반만** 사용(학생 약 30 + 교사 + TV).
- 이름은 저장하지 않는다. **반·조 번호만** 저장한다.

데이터 구조(안):

```
/sessions/{code}                 // 교사가 만드는 수업 방. code = TV에 띄우는 4자리
  meta: { hostUid, createdAt, cfg:{offSec:40, defSec:15, roundSec:540}, engineVer }
  round: { n, state:'lobby'|'live'|'done', startedAt }
  players/{uid}: { c, t, joinedAt, online }          // 반, 조
  pairs/{n}/{uid}: { room, role0:'off'|'def' }       // 라운드 n에서 내 방
  standings/{uid}: { w, d, l, pts }                  // 본인만 읽기
  teams/{c_t}: { pts, games }                        // TV용 조 집계 (교사 기기가 기록)

/rooms/{roomId}
  meta: { session, n, a:uidA, b:uidB, first:uidA, engineVer }
  state: { drive:1|2, down, goalNow, conv, phase, deadlineOff, deadlineDef }
  score/{uid}: number
  downs/{k}: { play, mode, throw, result, shownDef, actualDef, disguised }   // 결과 확정 뒤 기록
  final: { winner: uid|'draw', at }

/picks/{roomId}/{k}/{uid}        // 스냅 전 비공개 선택
  def: { actual, shown }  또는  off: { locked:true }
```

**보안 규칙 방침**
- 로그인(익명)한 사용자만 읽기/쓰기.
- `/rooms/{roomId}`는 그 방의 두 uid와 교사(hostUid)만.
- `/picks`의 수비 `actual`은 **스냅 전에는 상대가 읽을 수 없어야 한다.** 스냅 뒤 공격 기기가 판정에 쓸 수 있게 열린다. (규칙으로 구현하기 어려우면: 수비 기기가 스냅 신호를 받은 뒤 `actual`을 `/rooms/.../downs`에 공개 기록하는 2단계 방식으로.)
- `standings/{uid}`는 본인과 교사만. `teams`는 세션 참가자 읽기 가능.
- 세션·방은 하루 지나면 지운다(교사 화면 진입 시 오래된 것 정리).

※ Spark 요금제의 기능 범위(익명 로그인, 지역 선택, Functions 불가)는 구현 시작 때 공식 문서로 다시 확인할 것.

## 7. 화면

**학생 (`versus.html`)**
1. 입장: 수업 코드 4자리 + 반·조 (조 보관함 로그인을 했다면 반·조 자동 입력)
2. 대기실: "선생님이 시작하면 상대가 정해져요"
3. 공격 화면: 기존 작전판 + 작전 시계 + "수비: (shown 대형 / 고르는 중)"
4. 수비 화면: 대형 5개 큰 버튼 + 위장 토글(남은 횟수) + 현재 상황(몇 번째 공격·골까지 야드·상대 점수) + 작전 시계
5. 공개 카드: 실제 수비·위장 여부·던진 곳·결과 + [다시 보기]
6. 판 종료: 승/무/패, 내 전적, "다음 라운드를 기다려요"

**교사 (`host.html`)**
- 세션 만들기(코드 표시) → 접속 인원·조 분포 → [라운드 시작] → 진행 현황(판별 다운·점수, 이름 없음) → [라운드 종료] → 다음 라운드
- 설정: 작전 시계·라운드 시간

**TV (`vsboard.html`)**
- 수업 코드, 라운드 남은 시간, 조별 평균 승점 막대. 개인 정보 없음.

디자인은 기존 FLAG GAME 화면 톤을 그대로 따른다.

## 8. 파일 구성과 안전 원칙

- **`index.html`·`board.html`·기존 Apps Script는 건드리지 않는다.**
- 대전 모드는 `index.html`을 복제한 `versus.html`에 만든다(기존 방식: 새 버전은 별도 파일로 올려 써 보고 교체 여부 결정).
- 엔진 구역(판정·수비 움직임·`simulate()`·`R`)은 수정 금지. 수정이 꼭 필요하면 멈추고 먼저 묻는다.
- Firebase가 안 되면(차단·한도 초과·오프라인) "대전을 쓸 수 없어요. 혼자 하기로 이동" 안내 후 `index.html`로 보낸다.
- 회귀 확인: 같은 문제 번호·같은 입력으로 `index.html`과 `versus.html`의 혼자 하기 결과가 같아야 한다.
- 수행평가 기간(2026. 11. 17. ~ 다음 주)에는 `flagplan`·`flagboard` 저장소에 손대지 않는다.

## 9. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| M0 | Firebase 접속 확인 페이지 1장(`ping.html`) | 학교 웨일북에서 "연결됨"이 뜬다 |
| M1 | 방 코드 직접 입력 1:1 (교사 화면 없이 2기기) | 두 기기에서 한 판이 끝까지 진행, 양쪽 장면·결과 일치 |
| M2 | 교사 세션·무작위 매칭·라운드·작전 시계·TV | 30대 동시 3라운드 무사고 |
| M3 | 조 대 조 허들 게임(5명이 각자 자기 라우트·수비 자리 선택) | 별도 설계 후 |
| M4 | 수비 1명 직접 조종(실험) | 별도 설계 후 |

M3·M4는 방 구조를 그대로 쓰도록 M1에서 `rooms`에 인원을 2명으로 못 박지 않는다.

## 10. 검증 항목

- 결정론: 같은 `{play, actual, throw}` 100개를 Chrome·웨일북·iPad에서 돌려 결과가 모두 같다.
- 시계: 한쪽 기기 시계를 2분 틀어 놓아도 작전 시계가 양쪽에서 같이 끝난다.
- 끊김: 플레이 중 새로고침 → 같은 방·같은 다운으로 복귀. 30초 넘게 안 돌아오면 남은 다운은 시간 초과 규칙으로 자동 진행.
- 홀수 인원, 중간 입장(다음 라운드부터 참가), 중간 퇴장.
- 스냅 전에 공격 기기에서 수비 `actual`을 읽을 수 없다.
- 동시 접속 35개에서 지연 체감 없음.

## 11. 아직 정하지 않은 것

1. 작전 시계 40초/15초의 실제 적정값 (수업에서 측정)
2. 홀수 인원의 연습 경기 승점(기본 1점)
3. 후공이 선공 점수를 알고 시작하는 유불리를 그대로 둘지
4. 공개 카드 뒤에 질문 한 줄(기존 `runQuestion` 식)을 넣을지
5. 대전 결과를 시트에 남길지(기본: 남기지 않음, Firebase에서 하루 뒤 삭제)

## 12. 선생님이 직접 해야 하는 일

1. Firebase 프로젝트 생성 (개인 구글 계정)
2. Authentication → 익명 로그인 켜기
3. Realtime Database 만들기 (지역은 아시아 권장)
4. 웹 앱 등록 후 설정값(`apiKey`, `authDomain`, `databaseURL`, `projectId`, `storageBucket`, `appId`) 전달
5. 학교 웨일북으로 `ping.html` 열어 접속 확인

자세한 순서: [`firebase/설정안내.md`](../firebase/설정안내.md)
